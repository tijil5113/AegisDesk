Security / Privacy

What AegisDesk actually does with data

Server-side credentials

The browser talks to AegisDesk API routes such as /api/mail/send, /api/music, /api/chat, /api/intent, /api/gnews, and /api/news. Client bundles are not supposed to contain provider secrets. /api/intent accepts a query and a catalog of allowed action ids; it cannot run arbitrary tools.

Authentication

Accounts use email and a password hashed with bcrypt. Sessions are stored as hashed tokens in PostgreSQL and issued as HttpOnly, SameSite=Lax cookies (Secure in production). Sign-out revokes the server session. An optional access-code allowlist remains for private deployments. Passwords are never stored in plaintext or returned to the browser.

Database

Account records live in PostgreSQL when DATABASE_URL is configured. Notes, tasks, bookmarks, and similar workspace data stay in this browser so adding a database does not erase existing local data.

Browser limitations

AegisDesk cannot read your computer’s full filesystem, host CPU, unrestricted shell, or full OS clipboard history. Clipboard History only stores text copied through AegisDesk. Files is a virtual workspace. Terminal is simulated. System Monitor reports browser runtime metrics. Browser embedding is blocked by many sites; AegisDesk does not attempt to bypass that.

Local persistence

Tasks, notes, bookmarks, settings, themes, mail sent history, and similar workspace data are stored in this browser (localStorage or IndexedDB). Clearing site data removes them. Redesigns keep existing storage keys so upgrades do not silently erase that data.

This page does not claim military-grade encryption, zero knowledge, or that the product is unhackable.
